# /rootgraph-table

Ручное заведение узлов графа Rootgraph для схемы БД **пользовательского**
проекта (не самого Rootgraph) — `Table`/`Column` — и связей `READS`/`WRITES`
между кодом и этой схемой. Как и `Component`
(`/rootgraph-component`), это декларативная точка изменения: автоматический
разбор SQL/ORM из кода ненадёжен сразу на 22 языках/ORM, где текст запроса
может собираться из фрагментов, а не быть буквальной строкой — точность
важнее полноты. Не вызывай эти инструменты "на всякий случай", только когда
пользователь явно описывает схему БД или то, какой код к ней обращается.

Перед первым использованием в проекте убедись, что Rootgraph вообще
подключён (`rootgraph_status`, `configured: true`) — если нет, не выполняй
дальше ничего из этого файла, скажи пользователю, что нужен `rootgraph_init`.

Если `rootgraph_status` вернул `project_locked` (или любой вызов `rootgraph_*` ответил «проект заблокирован» / «проект удалён» / «доступ отозван») — немедленно остановись, ничего не повторяй и не запускай субагентов, передай пользователю сообщение из ответа (код и ссылку на тарифы) и больше не вызывай `rootgraph_*`.

Аргументы команды: `$ARGUMENTS`. Разбери первое слово как подкоманду:

## `add <table> [описание...]`

Например: `/rootgraph-table add users Таблица пользователей`.

1. Вызови `rootgraph_table_add(name, description)`.
2. Покажи результат одной строкой: `name — description`.

## `list`

Вызови `rootgraph_table_list` без параметров, выведи таблицей
`name | description`, отсортированной так, как её вернул инструмент.

## `column <table> <column> [описание...]`

Например: `/rootgraph-table column users email Почта пользователя`.

1. `table` должна быть уже заведена (`add`) — если инструмент вернёт "таблица
   не найдена", предложи сначала выполнить `add`, не пытайся угадать похожее
   имя.
2. Вызови `rootgraph_column_add(table, name, description)`.
3. Покажи результат одной строкой: `table.name — description`.

## `link <table>[.<column>] <reads|writes> <file|symbol> <путь-или-имя>`

Например:
- `/rootgraph-table link users.email reads file server/internal/store/users.go`
- `/rootgraph-table link users writes symbol store.CreateUser`

Заводит `(Symbol)-[:READS|WRITES]->(Table|Column)`:

1. Разбери `<table>[.<column>]` — если есть точка, `table` и `column` до/после
   неё; без точки — связь идёт на таблицу целиком.
2. `<reads|writes>` — ровно одно из двух, не переспрашивай "уверен ли ты",
   если пользователь уже написал одно из этих двух слов явно.
3. `<file|symbol>` определяет, какой параметр заполнять — `file_path` или
   `symbol_name` — ровно один из них.
4. Вызови `rootgraph_table_link(table, column?, kind, file_path?, symbol_name?)`.
5. После `file`-формы: инструмент относит связь ко ВСЕМ символам, у которых
   `file_path` совпадает буквально — предупреди пользователя, что при
   появлении новых символов в этом файле после переиндексации связь на них
   не подхватится сама, `link` нужно будет повторить.
6. Если пользователь не указал, какую из двух форм (`file`/`symbol`) имеет в
   виду, уточни явно, а не гадай — то же правило, что у `/rootgraph-component`.

## Без аргументов — короткий интерактивный опрос

Если `$ARGUMENTS` пуст, не вызывай инструменты сразу — сначала спроси одним
сообщением: заводим новую таблицу, колонку существующей таблицы, или
связываем код с таблицей/колонкой? Дальше действуй по соответствующей секции
выше, задавая по одному уточняющему вопросу за раз (таблица → колонка →
описание, и так далее) — тот же принцип, что у `/rootgraph-component` и у
мастера опросника конвенций (`/rootgraph-conventions`):
пошагово, не одной длинной формой.
