# /rootgraph-component

Ручное заведение узлов графа Rootgraph, которые не появляются сами при
индексации кода: `Component` (сервис/хранилище/хост/домен/прокси) и
`CAN_ACCESS` (кто и как может до компонента достучаться). В отличие от
`Symbol`/`Edge`, это редкая, декларативная точка изменения — не вызывай её
"на всякий случай", только когда пользователь явно описывает архитектуру или
доступ к ней.

Перед первым использованием в проекте убедись, что Rootgraph вообще
подключён (`rootgraph_status`, `configured: true`) — если нет, не выполняй
дальше ничего из этого файла: скажи пользователю по полю `notice`, что проект не подключён
(`rootgraph init` в терминале, код приглашения в чат присылать не нужно).

Если `rootgraph_status` вернул `project_locked` (или любой вызов `rootgraph_*` ответил «проект заблокирован» / «проект удалён» / «доступ отозван») — немедленно остановись, ничего не повторяй и не запускай субагентов, передай пользователю сообщение из ответа (код и ссылку на тарифы) и больше не вызывай `rootgraph_*`.

Аргументы команды: `$ARGUMENTS`. Разбери первое слово как подкоманду:

## `add <kind> <name> [описание...]`

Например: `/rootgraph-component add service httpapi HTTP-слой сервера`.

1. `kind` должен быть одним из `service`/`datastore`/`host`/`domain`/`proxy`
   — если пользователь написал что-то другое, спроси,
   какой из пяти вариантов ближе всего, не пропускай мимо валидации молча.
2. Вызови `rootgraph_component_add(kind, name, description)`.
3. Покажи результат одной строкой: `kind/name — description`.

## `list`

Вызови `rootgraph_component_list` без параметров, выведи таблицей
`kind | name | description`, отсортированной так, как её вернул инструмент.

## `link <component> depends-on <other-component>`
## `link <component> file <путь>`
## `link <component> symbol <имя-символа>`

Три формы одной операции — ровно один из `depends_on`/`file_path`/
`symbol_name` в вызове `rootgraph_component_link(component, ...)`. Если
пользователь не указал, какую из трёх форм имеет в виду (просто написал
`link httpapi graph`), уточни явно, а не гадай: "graph" — это другой
компонент (DEPENDS_ON) или файл (PART_OF)?

После `file`-формы: инструмент относит к компоненту ВСЕ символы, у которых
`file_path` совпадает буквально — предупреди пользователя, что при появлении
новых символов в этом файле после переиндексации (новая функция и т.п.)
связь на них не подхватится сама, `link` нужно будет повторить.

Путь — один файл от корня проекта (`./` и абсолютный путь внутри проекта
инструмент приводит к нужному виду сам). Каталог и маска не принимаются:
связывай файлы по одному. Если в ответе `linked: 0`, тихого нуля не бывает —
там есть `reason` (`unknown_path`, `not_a_file`, `excluded`, `secret_tombstoned`,
`no_symbols`, `not_indexed`, `symbol_not_found`) и `message` с объяснением и тем,
что делать. Передай пользователю `message` и не повторяй вызов вслепую: файл из
`.gitignore`, исключённый или похожий на секрет привязать не к чему (секретный
файл из `.gitignore` не предлагай убирать из игнора: его значения только в
хранилище), а при `not_indexed` нужен `rootgraph index`.

## `access grant <component> <device|user> <ref> <mechanism> [ref-на-секрет]`

Например: `/rootgraph-component access grant jump-151 user a@example.com ssh-key ~/.ssh/id_prod`.

КРИТИЧНО: `ref-на-секрет` (последний позиционный аргумент) — это путь/имя
секрета (например `~/.ssh/prod_key` или `"1Password: RunGPU prod"`), а НЕ сам
пароль/ключ/токен. Если то, что дал пользователь, похоже на реальный секрет
(длинная случайная строка, начинается с "ssh-rsa"/"ssh-ed25519", похоже на
API-ключ) — не отправляй это в `rootgraph_access_grant`, объясни, что граф
хранит только ССЫЛКУ на секрет, и попроси путь/название хранилища секретов
вместо значения.

Вызови `rootgraph_access_grant(component, principal_type, principal_ref, mechanism, ref)`.

## `access list <component>`

Вызови `rootgraph_access_list(component)`, выведи таблицей
`principal_type | principal_ref | mechanism | ref | granted_at`.

## Без аргументов — короткий интерактивный опрос

Если `$ARGUMENTS` пуст, не вызывай инструменты сразу — сначала спроси одним
сообщением: заводим новый компонент, связываем существующие, или выдаём/
смотрим доступ? Дальше действуй по соответствующей секции выше, задавая по
одному уточняющему вопросу за раз (kind → name → description, и так далее) —
это тот же принцип, что у мастера опросника конвенций (`/rootgraph-conventions`):
пошагово, не одной длинной формой.
